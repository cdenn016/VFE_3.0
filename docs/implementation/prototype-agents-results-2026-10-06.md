## Model

The block MLP becomes the minimal agent model with a static library of M = `block_mlp_expansion` * K prototype agents. Template a carries the belief p_a = N(nu_a, Lambda_a) with Lambda_a = diag(lambda_a), lambda_a = exp(log_lambda_a), and the prior weight pi_a = softmax(log_pi)_a; the token's working belief N(xi_i, C_i) is the receiver. Query and sending maps are the identity (S = T = I, full rank) and the channel noise is absorbed into Lambda_a, so the record covariance is W_ia = C_i + Lambda_a. Under `block_mlp_inference="exact"` the block returns the moments of the exact mixture posterior of Proposition ma:prop:minimal (a), (d). The template weights are w_ia = softmax_a(log pi_a + log N(nu_a; xi_i, C_i + Lambda_a)). With the residuals r_ia = W_ia^{-1} (nu_a - xi_i) the block forms u_i = sum_a w_ia r_ia, the averaged precision Lambda_bar_i = sum_a w_ia W_ia^{-1} and the between-template spread R_i = sum_a w_ia r_ia r_ia^T - u_i u_i^T, and it returns the mean xi_i^+ = xi_i + C_i u_i and the covariance C_i^+ = C_i - C_i (Lambda_bar_i - R_i) C_i. The covariance is evaluated in the equivalent cancellation-free form C_i^+ = C_i Psi_i + C_i R_i C_i with Psi_i = sum_a w_ia W_ia^{-1} Lambda_a, which follows from C - C W^{-1} C = C W^{-1} (W - C) = C W^{-1} Lambda_a. Both terms are positive semidefinite by construction and the first is positive definite (it is the w-average of P_ia = (C_i^{-1} + Lambda_a^{-1})^{-1}), so a sharp template that pins the belief never produces a difference of two large matrices. In float32 at lambda/c = 1e-7 the diagonal of C^+ stays positive and within 1e-3 relative of float64 (test below). The spread R is accumulated with the weighted form of Chan, Golub and LeVeque's pairwise variance update, so it is a sum of positive semidefinite terms in every tiling.

Under `block_mlp_inference="mean_field"` (the default) the block runs the first structured-mean-field step of the same record model started at the token's prior (Proposition ma:prop:mean_field). The label update r_ia = softmax_a(log pi_a - KL(N(xi_i, C_i) || p_a)) is exactly `GaussianTemplateBlockMLP.responsibilities`, evaluated by the same three-matmul expanded square (only diag C_i enters because Lambda_a is diagonal). The receiver update is the power posterior with D_i = sum_a r_ia / lambda_a and eta_i = sum_a r_ia nu_a / lambda_a. Its covariance is P_i = (C_i^{-1} + diag D_i)^{-1}, evaluated as the product D^{-1/2} (I + D^{1/2} C_i D^{1/2})^{-1} D^{1/2} C_i; its mean is xi_i^+ = P_i (C_i^{-1} xi_i + eta_i) = xi_i + P_i (eta_i - D_i * xi_i); and C_i^+ = P_i. The product form follows from the push-through identity (I + D^{1/2} C D^{1/2})^{-1} D^{1/2} = D^{1/2} (I + C D)^{-1} and needs neither C^{-1} nor a subtraction; the matrix I + D^{1/2} C D^{1/2} has eigenvalues of at least one, and for a diagonal C it reduces to P_ik = c_ik / (1 + c_ik D_ik). The mean-field covariance omits the between-template spread, as the docstrings say. In both modes the update is a precision-weighted combination of the token's own mean and the template means: the values are tied to the template means (no free value matrix) and the residual is derived, the coefficient of xi_i being I - C_i Lambda_bar_i (exact) or P_i C_i^{-1} (mean field). For shared isotropic C_i = cI and Lambda_a = lambda I the exact weights are softmax_a(beta nu_a.xi - beta |nu_a|^2 / 2 + log pi_a) with beta = 1/(c + lambda) and xi^+ = (lambda xi + c sum_a w_a nu_a)/(c + lambda), which at lambda -> 0 is the modern Hopfield retrieval of Ramsauer et al. (2020, arXiv:2008.02217) with the stored patterns nu_a as both keys and values; the class docstring states this reading. Dropout (the block's `block_mlp_dropout`) multiplies the mean increment xi^+ - xi only and never the covariance.

## Code

The mathematics lives in a new module `vfe3/model/prototype_agents.py` as pure functions with LaTeX docstrings and shape comments: `covariance_layout`, `covariance_diagonal`, `template_kl_logits`, `prototype_exact_posterior` (returning `ExactPrototypePosterior(xi_plus, delta_xi, C_plus, weights, u, Lambda_bar, R)`) and `prototype_mean_field_posterior` (returning `MeanFieldPrototypePosterior(xi_plus, delta_xi, C_plus, responsibilities, D, eta)`). The three computing functions (`template_kl_logits` and the two posteriors) run with autocast disabled and IEEE fp32 GEMMs (`ieee_fp32_matmul`), at float64 when an input is float64 and float32 otherwise. The working covariance may be diagonal `(..., K)`, dense `(..., K, K)` or compact blocks `(..., G, b, b)` with G b = K, and every covariance output uses the input layout. Because Lambda_a is diagonal, W_ia and C_i^{-1} + diag D_i keep the block structure, so the linear algebra runs block-batched with block size 1 (elementwise), b or K. The exact spread C R C couples blocks; a diagonal or block layout returns the diagonal (the diagonal blocks) of C^+, which is the moment-matched member of that family (the KL(p || q) minimizer over block-diagonal Gaussians keeps the diagonal blocks), and it needs only the diagonal (the diagonal blocks) of R, so the block layout costs O(N M K d) rather than O(N M K^2) for the spread. The dense layout forms the dense spread.

On the exact path rows (tokens) are independent and are tiled, and the templates of a row tile are processed in chunks merged by an online log-sum-exp accumulation in one pass, so each pair is factorized once in the forward. The tile budget `tile_bytes` (32 MiB) counts two pair tensors per pair, as the noisy-query routing tiles do, so it bounds each pair tensor at 16 MiB. It does not bound the pair data a tile holds, because a tile forms several pair tensors (the diagonal tile up to nine: W, W^{-1}, nu - xi, r, the product (nu - xi) r, log W, the deviation of r from the tile mean, its square and W^{-1} Lambda) and autograd saves several of them. At the launcher tile, whose pair tensor is 16 MiB, the process peak working set rose by 6.3 pair tensors in a forward without gradients, 7.3 in a forward with gradients and 10.7 in a forward and backward of the unchunked tile on the diagonal layout, and by 5.2, 5.2 and 6.9 pair-matrix tensors on the block layout (G = 4, b = 32, one token by 1,024 templates); each figure comes from a fresh process measured with psutil after a tiny warm-up. With gradients on and more than one tile, each tile runs under a non-reentrant `torch.utils.checkpoint` (it draws no random numbers, and it carries its own IEEE GEMM policy so the recompute reproduces the forward). Block and dense layouts factor every (token, template, block) matrix with zero jitter and no repair; failures are collected on the device and raised as one `ValueError` after the last tile (one host check), and a diagonal layout raises the same way if some c + lambda is not positive.

`vfe3/model/block_mlp.py` adds `PrototypeAgentBlockMLP(embed_dim, expansion, dropout, *, covariance_contract="passthrough", inference="mean_field", template_init_variance=10.0)` with parameters `nu` (M, K), `log_lambda` (M, K) and `log_pi` (M,), methods `posterior`, `forward_moments`, `forward` and `statistics`, and the registry entry `"prototype_agents"`: `covariance_kinds = {"passthrough", "posterior"}`, `gauge_class = "coordinate_nonintertwiner"`, not intertwiner compatible, `parameter_count_per_layer = 2 e K^2 + e K`, `matmul_flops_per_layer = 8 e K^2` (the four K x M matmuls of the mean-field mean update: two for the label logits, one each for D and eta), `extra_flops_per_layer = K^3/3 + 6 K^2` on the full layout (one dense Cholesky and three K^2 products per token), `diagonal_extra_flops_per_layer = 7 K`, a `posterior` branch in `BlockMLPRegistration.flops_per_token` that adds 2 K^3 + 4 K^2 on the full layout (the Cholesky solve with K right-hand sides that forms P, its two diagonal scalings and the symmetrization, next to the existing `delta_full` branch; on the diagonal layout P is already formed for the mean, so the contract adds nothing), and report labels `prototype_agents_mean_only_nonintertwiner` / `prototype_agents_posterior_covariance_nonintertwiner`. A new registration field `factory_options` (default empty) names the keyword options a factory reads beyond the shared ones; `build_block_mlp` gained `inference` and `template_init_variance` keywords and forwards them only to factories that declare them, so the four existing factories are called exactly as before. `PROTOTYPE_TILE_BYTES` is the module default of the instance attribute `tile_bytes`, which is not module state.

`vfe3/model/frame_actions.py` adds `reference_covariance_compact(mu, sigma, frame)`, which returns C_i = U_i^{-1} Sigma_i U_i^{-T} as blocks `(..., N, G, d, d)` for diagonal beliefs on a compact block frame (the block shape is read from the frame) and as the dense `reference_covariance` otherwise, and `local_covariance(mu, C, frame, *, diagonal)`, which maps either layout back to Sigma_i = U_i C_i U_i^T or its diagonal. `vfe3/model/block.py::_reference_coordinate_block` passes that compact C_i (instead of diag C_i) to a prototype-agent block and, under `block_mlp_covariance="posterior"`, returns Sigma^+ = U C^+ U^T in the belief's layout (its diagonal for diagonal beliefs). The Gaussian-template and coordinate paths are unchanged, and a passthrough contract still returns the incoming covariance object. `vfe3/model/model.py` passes the two new settings to `build_block_mlp`.

## Configuration

Two fields follow `block_mlp_expansion` in `vfe3/config.py`: `block_mlp_inference: str = "mean_field"` ("mean_field" | "exact", read only by `prototype_agents`) and `block_mlp_template_init_variance: float = 10.0` (initial lambda_a, finite and positive, booleans refused). The comments of `block_mlp_mode`, `block_mlp_covariance` and `block_coordinates` name the new values. `block_mlp_covariance="posterior"` is admitted only by `prototype_agents`, through the registry's `covariance_kinds`. Under `block_coordinates="reference"` the mode list now admits `prototype_agents` and the covariance check admits `posterior` (still refusing `delta_full`). `per_type_hidden_bias` is refused for this mode by the existing coordinate-hidden-layer rule, and the module rejects a `hidden_bias` argument. `inactive_fields()` reports `block_mlp_inference` and `block_mlp_template_init_variance` unless `use_block_mlp` is on with `prototype_agents`, and reports `block_mlp_activation` and `block_mlp_covariance_floor` under `prototype_agents`. No existing default changed, and `tests/profiles.py` lists both new fields at their defaults. Initialization mirrors `GaussianTemplateBlockMLP`'s template means: nu is uniform in (-K^{-1/2}, K^{-1/2}) from the global stream, log_lambda = log(`block_mlp_template_init_variance`) and log_pi = 0. At lambda = 10 and token variances near 1 the initial pull toward the templates is c/(c + lambda) = 1/11, about 9 percent per layer, in both inference modes (the `statistics` gain fraction reproduces 1/11 at initialization). All three tables train at the block-MLP rate (`m_block_mlp_lr`, falling back to `m_p_mu_lr`). The template means `nu` sit in the block-MLP group (aux role `block_mlp`) under the global `weight_decay`; at the user's decision (follow-up, `docs/2026-10-06.md`) log_lambda and log_pi sit in a second group at the same rate with `weight_decay=0`, because decoupled decay would pull log_lambda toward 0 (lambda toward 1, sharper templates than the initialization) and log_pi toward a uniform prior. `gaussian_template` keeps its single decayed group. A default-config model has no new parameter, buffer or state-dict key; a `prototype_agents` model stores `block_mlps.{l}.nu`, `block_mlps.{l}.log_lambda` and `block_mlps.{l}.log_pi`.

## Costs

Launcher shape (plan Section 5): K = 128, H = 4, d = 32, N = 128, batch 32, 4 layers, M = 8 K = 1024, float32, so T = 4,096 tokens per layer. The block acts per token, so its cost is linear in T. Parameters per layer: coordinate MLP 2eK^2 + (e+1)K = 263,296; `gaussian_template` 3eK^2 + eK = 394,240; `prototype_agents` 2eK^2 + eK = 263,168. The mean-field path in local diagonal coordinates executes 8 e K^2 = 1.05 MFLOP of matmul per token, 4.3 GFLOP per layer forward, against 2.1 GFLOP for the coordinate MLP and 3.2 GFLOP for `gaussian_template`; it saves the (T, M) logits and responsibilities, 16 MiB each per layer, and needs no tiling. The exact path in local diagonal coordinates evaluates T M = 4.2 million pairs, T M K = 5.4e8 pair elements, at about 10 elementwise operations each for the mean and 17 with the posterior covariance (5.4e9 and 9.1e9 operations per layer, memory bound); a tile is 32 tokens by 1,024 templates (a 16 MiB pair tensor; the measured peaks of 6.3 to 10.7 such tensors are in the Code section), 128 tiles per layer, one pass. In reference coordinates with diagonal beliefs on the block frame the exact path factors T M H = 16.8 million 32 x 32 matrices per layer: about 1.8e11 FLOP for the Cholesky factors and 2.2e11 in total for the mean, about 6.6e11 with the posterior covariance (adding `cholesky_inverse` and the Psi and spread contractions); a tile is one token by 1,024 templates, 4,096 tiles per layer. With dense working covariances (the `gaussian_full` family locally, or full beliefs in reference coordinates) the exact path factors T M = 4.2 million 128 x 128 matrices, 2.9e12 FLOP for the factors alone and about 9.2e12 with the posterior; a tile is one token by 256 templates, 16,384 tiles per layer. The mean-field path in reference coordinates adds H Cholesky factors of 32 x 32 and two block solves per token (about 0.06 MFLOP, 0.32 MFLOP with the posterior) to the 1.05 MFLOP of matmuls, plus the frame actions. ## Review fixes

The review of this feature raised five minor findings and no blocking or major one; the fix stage (Claude Opus 5.5, the implementer's model family) addressed all five. `template_kl_logits` is public but had neither the IEEE GEMM decorator nor an autocast guard, so it was safe only inside `prototype_mean_field_posterior`: called directly under CPU bf16 autocast at K = 8 and M = 16, its logits moved by up to 0.06 from the float32 evaluation (measured before the change). It now carries `ieee_fp32_matmul` and evaluates with autocast disabled at the compute dtype, like the posteriors, and a new test checks bitwise equality under bf16 autocast. The posteriors' numbers are unchanged, because they called it inside their own guard with inputs already in the compute dtype, for which `.to` returns the same tensor. The tile-budget sentence of this note claimed a 32 MiB bound on the pair data of a tile; the budget bounds each pair tensor, and the Code section, the comment on `PROTOTYPE_TILE_BYTES` and the docstring of `prototype_exact_posterior` now say so, with the measured peaks. The budget itself is unchanged, because plan Section 3.3 bounds single tensors. The build-metadata FLOPs reported the same figure for `passthrough` and `posterior` on the full layout although `posterior` executes the solve that forms P; `flops_per_token` now adds 2 K^3 + 4 K^2 there, and the docstring of `BlockMLPBuildMetadata` (`vfe3/contracts.py`, a docstring-only change in a file Feature A's worktree does not modify) states that for this mode the figure is the mean-field local-coordinate cost. The sharp-template limit of plan item 3.4(4) now also runs on the compact block layout (two more test cases), and the formulas of this note are set in prose instead of code blocks.

One reference-test assertion was corrected. `test_registry_metadata_and_factory_forwarding` in `tests/test_prototype_agents_reference_20261006.py` asserted that `flops_per_token` under `posterior` on the full layout equals L (8 e K^2 + K^3/3 + 6 K^2), the passthrough figure. Under `posterior` with a dense working covariance, `prototype_mean_field_posterior` also evaluates P = D^{-1/2} B^{-1} D^{1/2} C as `cholesky_solve(D^{1/2} C, L)` followed by the D^{-1/2} scaling and the symmetrization. The two triangular solves with K right-hand sides cost K^2 FLOPs per right-hand side each, 2 K^3 in all, and the two scalings and the symmetrization add 4 K^2, while the passthrough contract skips this work (`need_covariance=False`). The expected value therefore omitted executed work, and it contradicted the registry's own convention, which adds 4 K^3 for `delta_full`. The assertion now expects L (8 e K^2 + K^3/3 + 6 K^2 + 2 K^3 + 4 K^2) and carries a comment with the reason; nothing else in the reference file changed.

## Deviations from the plan

The covariance is evaluated as C Psi + C R C rather than literally as C - C(Lambda_bar - R)C; the two are equal in exact arithmetic (tested), and the evaluated form has no cancellation when a sharp template pins the belief. The mean-field P is evaluated as D^{-1/2} (I + D^{1/2} C D^{1/2})^{-1} D^{1/2} C instead of inverting C^{-1} + diag D, for the same reason and to avoid C^{-1}. The plan says that block inputs form the dense spread; the block layout returns its own layout (the diagonal blocks of C^+, the moment-matched block-diagonal member), which needs only the diagonal blocks of R, so that path is O(N M K d) instead of O(N M K^2) and exact for what it returns; only the dense layout forms the dense spread. `inactive_fields()` also reports `block_mlp_covariance_floor` under `prototype_agents`, because no prototype-agent path reads it (the plan names only `block_mlp_activation`). `matmul_flops_per_layer` is 8 e K^2, the four matmuls actually executed, rather than "about 10 e K^2". The chunk-boundary test checks equality to 1e-12 in float64, not bitwise identity: the online merge sums in a different order. Test item 4 checks the limits by first-order convergence instead of fixed absolute tolerances, because at finite lambda the deviation is the true O(1/lambda) or O(lambda) effect (an absolute 1e-8 bound failed at lambda = 1e10 on a covariance with entries near 11, where -C D C is 1.5e-8). The plan does not say how the two new settings reach the factory; `build_block_mlp` forwards them through the new `factory_options` registration field. The plan defines no diagnostics for this feature; the module offers a detached `statistics(mu, sigma)` method (template-posterior entropy and effective template count, gain fraction tr(C Lambda_bar)/K or tr(P diag D)/K, geometric-mean template variance, prior entropy) and nothing is wired into the metrics CSV, which would have touched the files Feature A edits for its own diagnostics. The row-11 post-hoc patch refuses this mode instead of conjugating it.

## Not done

GPU cost and GPU numerics were not measured; the CUDA path of `cholesky_ex`, `cholesky_solve` and `cholesky_inverse` under deterministic algorithms is untested here. `train_vfe3.py` and `ablation.py` carry the two new fields at their defaults with the mode documented in a comment (follow-up); `scaling.py` carries no entry, and `ablation.py` has no sweep arm for the mode. The build metadata FLOPs (`flops_per_token`) describe the mean-field path in the family's layout, including the posterior covariance on the full layout, and do not represent the exact path or reference coordinates. The CPU timings in the Costs section were measured before the review fixes and were not re-measured; the only fix on a timed path is the autocast guard inside `template_kl_logits`, which the mean-field posterior already ran under. The `statistics` diagnostics are not in the metrics CSV. No training run, no comparison of perplexity against the coordinate MLP, and no large-N experiment was made, so nothing here says whether the prototype-agent block helps the user's K = 128 run. The full test suite was not run.
