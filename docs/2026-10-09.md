## Opt-in learnable routing temperature and comparison-map tie

Two opt-in router fields follow the info-geometer findings of the audit; both default to `False`, and with both off the parameters, state-dict keys and forward values are unchanged. `learn_attention_temperature=True` gives every relational layer a parameter `routing_log_temperature` of shape (H,), initialized at zero, and routes at tau_{l,h} = kappa_h sqrt(d_h) exp(clamp(delta_{l,h}, -3, 3)) (`RelationalOperators.routing_temperature`), so the log-temperature is s_{l,h} = log kappa_h + delta_{l,h} and step 0 reproduces the configured temperature exactly (the model logits matched bitwise at kappa_beta = 0.7). The clamp window is that of the decoder's `decode_log_scale`. The Gaussian KL routing cost is invariant under (S_Q, S_K) -> (A S_Q, A S_K), so before this no learned parameter could set routing sharpness. The temperature applies on the kernel readout of `projected_predictive` and on the `projected_gradient` receiver; `predictive_readout="minimal_agent"` (temperature 1) rejects it. It joins the relational score optimizer group with no weight decay and the score learning rate. It acts after the `kl_max` clamp, so it cools only below the cap: a row whose admissible costs all sit at an absolute-reference cap stays uniform with zero temperature gradient (1e-17 roundoff in the test). The M4 routing decomposition (`vfe3/posthoc/routing.py`) reports itself not applicable under a learned temperature, since it assumes one temperature per head for all layers.

`tie_comparison_maps=True` (`projected_predictive` with the kernel readout only) stores no `raw_score_k` and scores with S_K := S_Q, so the self-pair cost vanishes (maximum |D_ii| 6.1e-16 in fp64 against 0.047 to 2.47 untied on the same fixture) and with identity frames D_ij equals the KL between the two beliefs pushed forward by the same S (checked against `torch.distributions` to 1e-10). Each layer loses K^2 parameters; the run artifact counts and `vfe3/posthoc/maps.py` read the tie. Tests: `tests/test_routing_temperature_tie_20261009.py`.

## Moment-matched covariance update: per-block weight-gradient GEMMs

The audit item on the blockwise moment-matched update (`RelationalOperators._predictive_covariance_update_blockwise`) proposed a (..., H, H, N, d^2) layout so that the pooling runs as one bmm without permute copies. That layout cannot be reached without changing the arithmetic. The bmm inside each einsum fixes the order of every forward reduction and, through its backward, every gradient reduction. Every route from T_h C_i to the pooling, and from the pooled blocks to the lifted and C_att contractions, then needs one copy, because O_h^{(l)} depends on the output block l on both sides of the sandwich and the token axis sits between the reduced pairs. Removing those copies would change the float32 rounding of the forward pass, which the bitwise goldens of `tests/test_son_phase0_20261005.py` forbid, so the copies stay.

A CUDA profile at the live width (K=128, H=4, d=32, N=128) found a larger cost. Three weight gradients (T through T_h^{(m)} C_{i,m}, and O through the C_att and residual-cross contractions) are bmm calls batched over the 4 head blocks. Each block's output is only 128 x 32, reduced over all B N d token entries. At B=32 each such GEMM took 3.6 ms, because only a few thread blocks run; one GEMM per block took 0.6 ms (microbenchmark, shared GPU). On CUDA these three contractions now run one block per call (`_per_block_bmm`), with each block's reduction order unchanged. On CPU they still run the batched `torch.bmm`. The diagonal spread is now added in place on the head diagonal of the pooled tensor, instead of being added as a materialized H x H expansion, which is exact. On CPU, outputs and all gradients equal the previous implementation bitwise in float32 and float64. The per-block form is checked against the batched form bitwise on CPU (`tests/test_blockwise_per_block_gemm_20261009.py`). The end-to-end GPU timing and the GPU rounding comparison were not run, because the GPU was in use for training. The dense route builds T_h C_i with a single unbatched GEMM and has no such batched weight gradient, so it is unchanged.

## Hot-path scheduling: query log-determinant, deferred frame checks, fused clip finiteness

Under `routing_kl_max_reference="row_min"` the kernel router reads the Gaussian KL only through row gaps, so the query log-determinant, a row constant of the cost, cannot affect routing. `relational_predictive_readout` now passes `row_invariant=True` to `relational_score`, which calls `projected_gaussian_kl(..., query_row_constant_grad=False)`: the query factorization and its certificate run without autograd, the returned costs, certificates and recovery decisions are bitwise those of the default, and when either role needs recovery the query factor is refactored with autograd because the factor-route trace reads it. The full-link receiver and the absolute reference keep the default call. In fp64 the loss and routing weights are bitwise unchanged and parameter gradients agree to 1e-10 relative; what is dropped is the autograd term of a forward-invariant row constant, which was roundoff plus, for gaps above `kl_max`, an artifact of the detached row minimum. In an in-process A/B at the live shapes (B=32, row_min) a step went from 928.6 to 892.5 ms (median of 8 interleaved rounds, on a shared GPU). The two posthoc covariance-replacement scorers accept the new keyword.

Raise-only certificates no longer synchronize on their own inside `train_step`'s forward: `vfe3.contracts.deferred_host_checks` queues the frame contract of `CanonicalFrameContext` and the transport inverse certificate (when no escalation certificate is formed), and the projected scorer's per-layer decision read (`vfe3.contracts.host_read`) resolves them first, in registration order, with their original exceptions. Anything still queued is resolved when the scope closes, before `backward`. The chart-radius check stays immediate because it guards the matrix exponential, `torch.unique` and the scorer's recovery decision select computation, and outside the scope every check runs at once. The per-role clip norms are taken with `torch.nn.utils.get_total_norm` before the fused finiteness transfer and applied with `clip_grads_with_norm_`, which is the decomposition of `clip_grad_norm_`, so their finiteness rides that transfer. A training step at the live config went from 29 to 26 host synchronizations. Tests: `tests/test_hot_path_syncs_20261009.py`; the clip spies of `tests/test_train.py` now patch `clip_grads_with_norm_`.

## Round-2 audit remediation

The second audit of the day (`docs/audits/audit-2026-10-09-round2.md`) was remediated except for item 1 (historical clamp-reference pins for old runs, which the user does not need), the manuscript items (held), the registered margin rule (the user's decision) and the items in the user's working files `train_baseline.py` and `ablation.py`. Every new field defaults to the previous behavior.

Comparison-space RoPE self-lock. Under `rope_space="comparison"` the pair cost is KL(N(a_i, G_i) || N(R_{j-i} a_j, R_{j-i} G_j R_{j-i}^T)), and its trace term tr(G_j^{-1} R G_i R^T) penalizes any rotation in proportion to the anisotropy of the projected covariances, which grows during training until each head attends to itself. `frame` RoPE, ALiBi and learned `pos_phi` do not rotate a covariance against a fixed one and do not show it. The opt-in `rope_comparison_covariance="rotation_invariant"` (`vfe3/geometry/rope.py` `rope_commutant_projection`, `vfe3/gradients/relational.py`) projects each projected covariance onto the commutant of the RoPE torus before scoring: one isotropic variance per rotated plane (the mean of its two diagonal entries), the full block on the unrotated pairs, and zero cross terms. R G R^T = G then holds exactly, and only the means rotate. The factor route is marked inactive under the toggle, because the projected covariance has no source root. Tests: `tests/test_rope_comparison_covariance_20261009.py`.
