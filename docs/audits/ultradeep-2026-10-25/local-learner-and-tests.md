Read the live `vfe3/local_learner/{core,learners,baselines}.py`, `local_learner_test.py`, its stage-0 tests, CPU runner and shared pytest fixtures; followed the October 21 design and results and October 4/20 causal-model and local-learning derivations. ## L1: Completed-run reuse ignores the experiment configuration (P2)

Location: `local_learner_test.py:136-139`, `175-180`, `243-247`; result records at `190-196` and `254-257`. `done_keys` uses only `(arm, d, seed)`. Stage S adds chunk length to the arm label but still omits stream count, training data budget, averaging schedule, learning rate, ridge, covariance floor, validation slice, particle count, and source version. The output rows also omit most of these settings. Editing `local_schedule` from `rm06` to `floor20`, changing the value behind a named schedule, or changing `backprop_lr`, while leaving the output directory unchanged, silently skips those arms as complete. This is a normal click-to-run workflow; the module docstring explicitly advertises editing CONFIG and resuming.

Evidence is the complete source path, not a claim that current stored Stage B results were generated under the wrong settings. The current WIP changes the stage from B to S, which uses a different filename and does not itself trigger this collision. Minimal fix: bind result reuse to the effective arm configuration, source identity and data/protocol identity; persist that configuration with each result. Refuse or create a separate output group when it differs. A tiny test can create one ordinary completed result, change the effective schedule, and require the new run to remain pending. Falsifier: a caller-level identity check before `done_keys`; none is present in the two launch paths.

## L2: A test module changes the dtype of every subsequently constructed test model (P2)

Location: `tests/test_local_learner_20261021.py:17`; shared fixtures in `tests/conftest.py:209-266`; CPU runner command construction in `run_cpu_tests.py:126-153`. The local-learner test calls `torch.set_default_dtype(torch.float64)` at module import. Pytest imports selected modules during collection, before running tests. The existing fixtures restore several process-wide model policies but do not restore or establish a default dtype. Thus including this file changes otherwise implicit float32 tensors and parameters throughout that worker, including tests collected earlier but executed afterward. Xdist workers collect the selected suite independently, so the mutation is not isolated to this file.

Executed evidence: `probes_initial.json`, `test_collection_default_dtype`, changes from `torch.float32` to `torch.float64` merely by importing this module. This undermines the intended float32 coverage and can increase CPU cost; no whole-suite pass or failure is asserted here. Minimal fix: explicit float64 construction in this file or a function-scoped fixture that sets and restores dtype, plus a collection-isolation check. Falsifier: a guaranteed pre-test reset to float32 or isolation of this module in its own process; the reviewed CPU lane provides neither.

## L3: The ridge transition update does not return its documented residual covariance (P3)

Location: `vfe3/local_learner/learners.py:152-159`; test gap at `tests/test_local_learner_20261021.py:118-146`. Write Sxx for the regressor second moment and Szx for the state/regressor cross moment. The code solves W = Szx (Sxx + rho I)^(-1), then sets Q = Szz - W Szx^T. The actual expected residual covariance at that fitted W is

$$R=Szz-W Szx^T-Szx W^T+W Sxx W^T.$$

Because Szx = W(Sxx + rho I), the code returns R + rho W W^T, before symmetrization and flooring. The unregularized shortcut was applied to a regularized solve. This can be a different, deliberately penalized objective if explicitly defined, but the design and implementation currently call Q the expected residual covariance. The existing M-step test checks only the quadratic W and sensor objectives, omitting Q.

Executed example in `probes_initial.json`: one-dimensional latent state, two tokens, ridge 1, fitted G = 0.5, true residual Q = 1.25, computed Q = 1.5. Starting at the same W and Q = 1.25 raises the conditional Gaussian noise objective from 0.6115718 to 0.6193992. The live default ridge is 1e-6; a material effect on existing runs has not been demonstrated. Minimal fix: compute the complete residual expression, or subtract rho W W^T from the shortcut, and test the joint transition/noise objective with a non-negligible ridge. Falsifier: a declared Q-dependent ridge prior whose intended optimum is exactly this formula; the current specification contains no such contract.

## Improvements and limits

The n-gram reference in `local_learner_test.py:232-240` invokes `ngram_nll` afresh for every smoothing constant. `baselines.py:18-24` rebuilds all count arrays up to the requested order each time. For the seven-value grid, an identical training corpus is counted repeatedly and lower-order tables are rebuilt across orders. Separate count construction from scoring and reuse the count tables; vectorize held-out count lookups where memory permits. This is a source-based performance opportunity, with no claimed measured speedup.

Persist the fitted `Params` alongside complete configuration and data identity. Current result files preserve summary scores but no trained state, so improved diagnostics and repeat particle-filter estimates require rerunning training. The `pf_subset_exact_bits` field at launcher line 132 is a finite-particle estimate, correctly qualified in the design but not in that field name. Rename or qualify it, record particle count and seed, and add repeated estimates or a particle-count convergence check before using a small filter/PF difference as a tight approximation bound. Stack-dependent RNG consumption and the seed based on the first pending run mean a resumed grouping changes those Monte Carlo draws; a per-run seed would make comparison easier. None of this invalidates the currently observed bits-per-byte values by itself.

The initial audit probes ran on CPU, one thread, using `C:/anaconda/python.exe` and torch `2.10.0.dev20251210+cu128` with CUDA hidden. No training grid, Monte Carlo scan, full suite, or GPU work was run. Existing local-learner unit tests include a two-million-draw Monte Carlo check; that check is intentionally excluded from the focused validation for this audit.
